# JFTP modernization plan

Modernize the desktop application on Windows while preserving the existing Swing workflows, FTP and FTPS modes, saved profiles, certificate decisions, localized resources and JavaHelp. Use the [PRD](PRD.md) for behavior and [ADRs](ADR/000-main-architecture.md) for technical scope. Keep the prior verified package available while qualifying each successive one.

| Phase | Change and commit boundary | Required evidence before proceeding |
| --- | --- | --- |
| 1. Record the baseline | Document source, dependencies and operational constraints. Add root and scoped agent guidance with matching Claude imports. | Source references and documentation links resolve. Versions come from the POM or a dependency probe. Review each guidance file against the scope it governs. |
| 2. Protect four workflows | Use existing coverage for local filtering, ZIP, profile compatibility and plain FTP. Keep startup resource tests as a separate gate. Characterize missing cases before changing the affected behavior. | Run the baseline suite and retain the expected visible outputs, persisted fixtures, FTP responses, and transferred bytes. Preserve expected behavior when changing a test runner. |
| 3. Restore Windows startup | Reproduce the extracted package failure. Point the batch launcher to the root application JAR using the launcher's location. Verify runtime selection and a clear missing-Java error. | Build, run from another working directory with spaces in the extraction path, check one disconnected tab and Help, then rerun all regression tests. Use an isolated home and a real loopback server when checking transfers. |
| 4. Qualify the modern toolchain | Make a dedicated Java 25 and Maven Wrapper commit. Isolate unused legacy entry points from the Windows desktop compilation. Pin lifecycle plugins and update packaging plugins in the same build increment. | Clean build with the accepted toolchain and verified download checksums. Extract the ZIP and exercise the existing launcher, resource lookup, connection, transfer and saved-site behavior. Compare actual JAR contents before and after. |
| 5. Upgrade the test stack | Move JUnit 3 tests to the supported JUnit Jupiter runner while preserving their assertions and fixed profile fixtures. Keep the real MINA server test-scoped. | Same behavior checks run and pass. Exercise a deliberately failing assertion or targeted negative case to confirm test discovery. Record the effective dependency tree and exact versions. |
| 6. Modernize code in slices | Start with a small, well-covered component using typed APIs and resource cleanup. Follow with session action boundaries, then worker and tab ownership. Change one behavior seam per commit. Keep protocol calls, modes, filters, naming, retry/abort semantics and user prompts observable. | Re-run automated tests and exercise the changed flow in the packaged client. For session changes, prove two independent tabs and that pending work cannot update a replacement tab. Compare payload hashes and terminal session outcomes. |
| 7. Qualify legacy dependencies and storage | Probe the exact FTP API on JDK 25 with plain, opportunistic, explicit and implicit SSL modes, active and passive data, bad credentials, certificate refusal, proxy and abort. Verify JavaHelp content and keyboard context. For storage work, first prove legacy favorites, preferences and both JKS stores reopen. | Record each mode using a controlled endpoint under default JDK TLS policy. Refuse a library substitution until it preserves the qualified behavior. Any new migration interaction, file format or credential policy needs its own approved scope. |
| 8. Release the verified ZIP | Check a clean extraction from a different working directory and an isolated copy of a supported legacy profile. Record the JDK, Maven, plugins, runtime checksums and screenshots. | All required Windows and ADR gates pass. Verify copy and rollback with synthetic profile data before replacing anyone's working package. |

## How to respond to a failed gate

- Re-run the first failing check on the last verified build with the same fixture. If it passes there, treat the changed code or build as the likely regression. Repair it before proceeding.
- If both builds fail or the PRD, observed behavior and an accepted ADR disagree, record exact inputs, outputs and versions. Bring the material conflict to the user before changing the expected behavior.
- Keep failing transport or storage changes out of the release. Re-run the last qualified package with an untouched profile copy and restore the corresponding toolchain if required.
- In every modernization commit, review the root and affected nested agent guidance, the runbook and this plan. Update instruction and documentation facts alongside the code that changes them. Record evidence and any unverified gates with the affected phase.
